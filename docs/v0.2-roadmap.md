# resolver-oss v0.2 roadmap

**Date:** 2026-05-31
**Status:** v0.1.0-alpha shipped; below is the explicit list of known v0.1 gaps and v0.2 work, prioritized.

## Gaps in v0.1.0-alpha (in priority order)

### 1. End-to-end host integration (partial — LangMem only)

**Current state:** `LangMemE2EAdapter` runs real `MemoryStoreManager.ainvoke()` with monkey-patched `_apply_manager_output`. Smoke-tested on 5 scenarios; full 60-scenario run results land in `docs/langmem-e2e-results-2026-05-31.md`. Mem0 + Letta adapters in v0.1 are simulated-merge-layer only.

**v0.2:** wrap real `Memory.add()` for Mem0, real `client.agents.update_memory_block()` for Letta. Same pattern as `LangMemE2EAdapter` (real pipeline + adapter-specific policy injection point).

**Blocking:** Mem0 requires their Python client + their server; Letta requires a Letta deployment. Both are 1-2 day projects per host.

### 2. LongMemEval-S integration

See `docs/longmemeval-status.md` for the full writeup. Headline: $100-200 API cost per run; gated on real-world signal before invest.

### 3. Multi-write (>2 writers) support

**Current state:** all adapters and the `TypedMergePolicy.handle()` are pairwise (incoming vs N-existing, but typed policy only compares against `existing[0]` for the LLM call). For genuine N-way conflicts (3+ writers race-conditioning on the same subject), the policy collapses to pairwise.

**v0.2:** add `MergePolicy.handle_batch()` optional method to the Protocol. Adapters that need N-way pass all candidates; policies that implement it can reason globally.

**Blocking:** N-way conflict benchmark scenarios don't exist yet in agent-merge-bench. Would need bench v0.2 first.

### 4. Cross-provider model support

**Current state:** TypedMergePolicy hardcodes Anthropic Sonnet 4.6. The architecture would work with any chat LLM but it's not exposed.

**v0.2:** add `model_client: BaseChatClient` constructor param accepting any callable that takes a prompt and returns a string. Ship Anthropic wrapper as default; document the protocol so users can wire OpenAI, Gemini, local models, or even rule-based classifiers.

**Cost-low:** maybe 4-6 hours work. Could ship in v0.1.x patch.

### 5. PyPI publish

**Current state:** `pip install resolver-oss` 404s; install from source via `git clone + make install`.

**v0.2:** package + push to PyPI when the API surface is locked. Held back from v0.1 because the spec recommends keeping v0.1 alpha until at least one host adapter has been validated against real production traffic.

**Blocking:** owner-controlled action; requires PyPI account + token.

### 6. CI

**Current state:** tests run locally via `make test` (16/16 pass for the lib, 35/35 for the bench, plus 3 lib-adapter integration smoke tests). No GitHub Actions yet.

**v0.2:** GH Actions workflow running ruff + pytest on every PR. ~30 min setup.

### 7. Multi-agent-bench scenarios from real public agent traces

**Current state:** companion `agent-merge-bench` v0.1.0 ships 60 synthetic scenarios. Inter-labeller agreement was measured at 0.929 type / 1.000 decision on a 14-scenario stratified sample. Held-out validation skipped (designed but not executed; see `agent-merge-bench/research/synthesis/held-out-design-decision.md`).

**v0.2 (in agent-merge-bench, not resolver-oss):** execute the held-out plan + add 30 scenarios extracted from public agent traces (autogen, langgraph, agui). Without this, resolver-oss can't claim any "real-trace generalization" beyond what host adapters demonstrate.

### 8. Adversarial-against-self review of resolver-oss adapters

**Current state:** code-reviewer agent ran adversarial review on agent-merge-bench (3 critical + 5 high + 17 medium/low findings; critical fixed this session). NO equivalent review of resolver-oss adapters yet.

**v0.2:** spawn the same review against `src/resolver_oss/adapters/` to find the same class of bugs (claims-vs-code mismatch in adapter docs, type-mapping edge cases, schema invariant gaps in `MemoryWrite` conversions).

**Cost-low:** 1-2 hours agent budget.

## What's NOT on the v0.2 roadmap (and why)

- **A "MergePolicyChain" for composing policies.** Premature. Users can compose via `fallback=` today; we'd add a chain helper only once 3+ adopters need the same pattern.
- **Built-in caching at the policy layer.** Same reason — adopters can wrap; resolver-oss doesn't enforce a cache invariant.
- **Streaming policy decisions.** Decisions are atomic by design. Streaming the rationale wouldn't change the action.
- **MERGE-as-synthesis action.** The 5-action vocabulary deliberately omits "synthesize a new claim from two." If users demand it, v0.3 could add `Action.MERGE` + `MergeDecision.synthesized_content`.
- **Prompt-template overrides.** Hard-coded prompts in v0.1; adopters who need different prompts pass `classifier=callable`. Template API is high-blast-radius and easy to ship wrong.
- **External telemetry callbacks.** Adopters can wrap `policy.handle()` themselves to record stats. Out of scope.

## Acceptance criteria for v0.2 release

- (a) **At least 2 hosts have real-pipeline integration** (currently 1: LangMem). Mem0 or Letta brought up from simulation to real `Memory.add()` / `update_memory_block()`.
- (b) **End-to-end QA delta measured on LongMemEval-S** for at least one host. Reported per-axis. Even null result acceptable; the measurement is the deliverable.
- (c) **Cross-provider model support** at the constructor surface.
- (d) **Adversarial code review** of adapters cleared (or critical findings fixed).
- (e) **PyPI publish.**

(a)-(c) are real-engineering work. (d) is agent-budget. (e) is procedural.

## Conditional v1.0 cut

When v0.2 ships + ONE upstream host accepts a PR (or a maintainer publicly commits to evaluating one), cut v1.0 to signal API stability. Until then, stay 0.x.
